# @echopilot/harness-codex

Managed Codex app-server harness adapter (ticket H01, IMPLEMENTATION_PLAN.md §5.3): it spawns a
Codex app-server child of this project's choosing, drives it over stdio, and normalizes what the
server reports into v1 contract `EventEnvelope`s.

### Module layout (why there is no package.json here)

Like `apps/desktop`, this is a source-only workspace module rather than a pnpm workspace project:
the root `tsconfig.json` typechecks `packages/**/*.ts`, the tests run on the repository's `tsx`
toolchain, and `node scripts/generate-protocol.mjs` works without a manifest. Adding a manifest
would introduce a new workspace importer in `pnpm-lock.yaml`, and H01 deliberately owns only
`packages/harness-codex/`, `fixtures/harness/codex/`, and the desktop session view — never the
shared lockfile. The shared contracts are imported by relative path, exactly as the frozen
acceptance test does.

## Provenance — generated schemas, pinned version

Everything the adapter knows about the protocol comes from the JSON Schema bundle generated by the
installed, tested CLI:

```sh
codex --version                                       # codex-cli 0.154.0
codex app-server generate-json-schema --out schema
node scripts/generate-protocol.mjs                    # schema/ + src/generated/protocol.ts
node scripts/generate-protocol.mjs --check            # fail when the projection is stale
```

- `schema/` — the raw generated bundle, written by the script on demand (untracked: it is large
  upstream JSON and regenerating it is one command with the installed CLI).
- `src/generated/protocol.ts` — the tracked projection the adapter is allowed to rely on: client
  request/notification methods, server notification/request methods, `ThreadItem` discriminants,
  and `CommandExecutionApprovalDecision` values.
- `src/protocol.ts` — verifies at module load that every method and decision the adapter uses is
  present in that projection. A drifted constant fails loudly instead of being sent as a guess.

`SUPPORTED_SERVER_VERSION` is the `codex-cli` version the generated schemas came from (0.154.0).

## What the adapter does

```ts
const adapter = createCodexHarnessAdapter({ command, args, cwd, env, codexHome, scope });
await adapter.start();          // spawn + initialize → initialized handshake
const events = adapter.observe(); // AsyncIterable<EventEnvelope>, safe before or after start()
await adapter.send('…', 'delivery-1'); // thread/start (once) + turn/start(text input)
await adapter.interrupt('turn-1');     // turn/interrupt
await adapter.resume('thread-1');      // thread/resume; the next send() reuses the thread
await adapter.respondApproval('7', 'approve'); // answers only an observed pending request
await adapter.close();         // SIGTERM/EOF the child; never answers a pending approval
```

Transport is newline-delimited JSON-RPC on stdio. `command`/`args` are spawned directly as an argv
vector (never a shell) with a scrubbed environment plus the explicit `env` entries. `CODEX_HOME` is
always set by the adapter after those entries: pass an absolute, separately provisioned
`codexHome`, or omit it to create a fresh session-scoped temporary directory. Consequently the
child cannot silently fall back to the user's ambient `~/.codex`, desktop session, or
`NODE_OPTIONS`. A `CODEX_HOME` supplied through `env` is deliberately ignored.

`resume(threadId)` is limited to thread ids returned by `thread/start` to this adapter instance.
This prevents the managed child from using `thread/resume` as an attachment mechanism for an
arbitrary ambient Codex thread. Cross-process attachment is not part of H01's guaranteed surface.

### Notification normalization

| app-server notification | normalized event | trust |
| --- | --- | --- |
| `item/started` with a tool item (`commandExecution`, …) | `tool_started` | `tool_observed` |
| `item/completed` with a tool item | `tool_completed` | `tool_observed` |
| `item/completed` with `agentMessage` | `agent_message` | `agent_reported` |
| `thread/started`, `turn/started`, `turn/completed` | `session_state` | `tool_observed` |
| anything else (known but unmapped, or newer) | `unsupported` + raw `unsupportedKind` | `tool_observed` |

Every envelope satisfies the shared v1 contract (`schemaVersion: 1`, stable `sourceId`, strictly
increasing `sourceSequence`/`ingestSequence`, unique `eventId`, `payloadRef` + `contentHash`). Turn
scoped events carry `turnId`; `scope.sessionId` is the app-server thread id.

Events carry references, never inline content: the adapter does not expose hidden reasoning.
`item/reasoning/*` notifications are dropped outright, as are streamed content fragments
(`…/delta`, `…outputDelta`) — the completed item carries the final content. Only text the
app-server reports as a completed agent message becomes user-visible content.

### Approvals

A server → client approval request (`item/commandExecution/requestApproval`, `applyPatchApproval`,
…) is normalized to `approval_requested` with `sourceEventId` equal to the JSON-RPC request id.
The adapter does **not** answer it. `respondApproval(requestId, 'approve' | 'deny')` writes
`{ decision: 'accept' }` or `{ decision: 'decline' }` for exactly that id, and rejects when no
request is pending. Closing the session, a child exit, or any other failure drops pending requests
without answering: a companion failure can never auto-approve (or auto-deny) a guarded action.
Server requests the pinned schema does not describe are observed as `unsupported` diagnostics and
are deliberately left unanswered — answering would be guessing a payload shape.

### Compatibility and observe-only mode

`info()` reports the generated-schema version, the version the attached app-server reported in the
initialize response's `userAgent` (its first `name/version` token — `codex-cli/0.154.0` for a
`codex-cli` client, `<client>/0.154.0` otherwise), whether they match, and the capability list.
When they do not match, the adapter is observe-only:

- `capabilities()` is exactly `{ observe }`;
- `send`, `interrupt`, `resume`, and `respondApproval` reject without writing anything to the wire;
- unknown notification methods still stream as `unsupported` diagnostic events, so a newer server
  can be watched without being driven.

## Tests

```sh
node --import tsx --test packages/harness-codex/test/h01.acceptance.test.ts
```

The suite drives the adapter against `fixtures/harness/codex/fake-app-server.mjs`, a real stdio
child speaking the pinned protocol, and asserts against its wire journal: read-only fixture task
with interrupt/resume, approvals that stay pending until an authorized decision (and are never
auto-approved on failure), and the observe-only guarantees for an incompatible version.
